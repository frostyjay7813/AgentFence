Authorization that follows the action.

AgentFence binds AI-agent permissions to the exact action, resource, origin and task they were issued for — and verifies those bindings again at the execution boundary.

Not "agent may read"

An AgentFence authorization names one action, one resource, one origin and one task. There is no wildcard and no standing permission.

Verified again, at the boundary

The execution gate reconstructs the live context and re-checks every binding. A mismatch is a denial, not a warning.

Every decision leaves evidence

Allow or deny, each produces a receipt with integrity value, policy version and approval reference.

The honest scope. Modern agent protocols deliberately leave in-task authorization scope, validity and revocation semantics to implementations, credential issuers or extensions — A2A 1.0 states this explicitly. AgentFence demonstrates one implementation strategy for making those semantics explicit and execution-bound. It is a demonstration pattern, not a complete IAM system.

Interactive demonstration

An agent is authorized to read one customer record from one origin during one task. The action succeeds. Then the same authorization is replayed against altered contexts — every one is denied.

AWS infrastructure vs. AgentFence application logic

AWS infrastructure

API Gateway, Lambda, DynamoDB, CloudWatch, IAM. These provide hosting, the HTTPS surface, the evidence store and the execution identity.

AgentFence application logic

Canonicalization, integrity values, the binding check, the policy table, approval binding and the gate ordering. These are the product, and they are not provided by any AWS service.

Why the gate ordering is the security property

The gate runs a fixed sequence. Bindings are verified before policy is evaluated, so a capability substitution is reported as the true security reason instead of leaking which capabilities policy forbids.

0. request schema          → MALFORMED_REQUEST
1. authorization present   → MISSING_AUTHORIZATION
2. authorization integrity → INTEGRITY_MISMATCH   (tamper check FIRST)
3. registries              → UNKNOWN_AGENT / UNKNOWN_ORIGIN
4. validity window         → AUTHORIZATION_EXPIRED
5. BINDING MATCH           → *_MISMATCH             ← the core invariant
6. policy lookup           → NO_SUCH_POLICY         (no default-allow)
7. policy effect           → POLICY_DENY / REQUIRE_APPROVAL
8. approval (if required)  → APPROVAL_*
9. policy scope            → UNKNOWN_RESOURCE / UNKNOWN_ORIGIN
10. execute                → capability invoked

What this is not

Not a prompt-injection defense. Injection can cause an authorized agent to request a harmful action. AgentFence's contribution is that the request must still match an authorization issued for that exact context — it does not judge whether the original instruction was malicious.

Not a claim about MCP or A2A. MCP's authorization requirements are explicit and were hardened in 2026; AgentFence addresses the execution-boundary problem, which sits outside the protocol. A2A 1.0 deliberately defers in-task authorization semantics to implementations, credential issuers and extensions; AgentFence is one such implementation strategy.
